# AI 一线情报工作台 MVP PRD

**版本**：v1.5  
**状态**：正式基线  
**阶段**：开发前确认版  
**版本名称**：AI 一线情报工作台 MVP

## 1. 版本信息与定位
`v1.5` 的定位不是“AI 看板增强版”，而是把 `v1.4` 的离线试运行产物升级为一个可供产品负责人和销售管理者持续使用的 AI 一线情报工作台。

本期的核心不是再多做几张图，而是把一线 AI 相关信号沉淀为：
- 可观察的趋势
- 可下钻的销售分析
- 可追溯的业务结论
- 可回写的人工复核

统一工作台是本期唯一正式业务查看入口。

## 2. 目标用户与核心业务问题
目标用户固定为两类：
- 产品负责人
- 销售管理者

需要解决的核心业务问题：
- AI 在一线到底是升温、波动还是停滞。
- 哪些销售在持续推动 AI 相关表达、反馈和机会。
- 云诊室与云管家在 AI 上的趋势和问题是否一致。
- 当前 AI 信号中哪些值得继续投入，哪些只是噪声或泛趋势。
- 哪些结果可信，哪些需要人工复核并回流到系统。

## 3. 为什么 `v1.4` 不够
`v1.4` 已经证明链路可跑、结果可追溯，但仍存在以下不足：
- 趋势层主要停留在命中数量和覆盖率，不能稳定回答“是谁推动了变化”。
- 最小颗粒度仍以区域、战区和 `owner_hint` 为主，不能稳定下钻到销售个人。
- 结论层更多是标签与证据堆叠，缺少可直接用于判断的业务结论卡。
- `review_queue` 仍是待处理清单，不是正式复核工作流。
- HTML 看板是静态展示物，不是持续使用的业务工作台。

因此，`v1.5` 要解决的不是“展示更好看”，而是“结果更可判断、可行动、可学习”。

## 4. 版本目标
本期目标固定为四项：
- 建立统一 Web 工作台，替代 `v1.4` 的静态 HTML 报告。
- 建立以销售个人为最小颗粒度的趋势与行为分析视图。
- 建立可追溯的结论中心，把证据簇抽象成业务结论卡。
- 建立文件回写型复核闭环，让人工修正可进入下一轮分析。

## 5. MVP 范围
### 5.1 输入范围
- `2025-01` 至 `2026` 当前归档文档作为主分析范围。
- `v1.3` 冻结样本作为回归基线。
- `v1.4` 试运行中的复核结果作为复盘参考。

### 5.2 分析范围
- AI 提及趋势
- 销售个人维度的活跃度与渗透率
- 业务线分布：云诊室 / 云管家 / 混合 / 待判断
- 主体分布：销售自用 / 销售对外介绍 / 医生反馈 / 潜在 AI 机会
- 结论提炼：趋势、反馈、顾虑、机会、销售行为
- 人工复核与回写

### 5.3 产物范围
- 规范化中间层数据
- Web 工作台可读页面
- 复核任务与复核结果文件
- 结论卡和趋势摘要

## 6. 页面 / 模块范围
统一工作台包含五个模块：

### 6.1 总览首页
- 输出本期一句话结论
- 展示关键变化、重点机会、风险项、复核积压
- 提供后续下钻入口

### 6.2 趋势中心
- 月度趋势为主，周度趋势为辅
- 支持同比、环比、滚动观察
- 必须回答：
  - AI 提及是否上升
  - 是更多销售开始提 AI，还是少数销售提得更频繁
  - 哪类主体变化明显
  - 哪条业务线变化更显著

### 6.3 销售分析中心
- 最小颗粒度固定到销售个人
- 必须支持：
  - 长期活跃销售识别
  - 新近活跃销售识别
  - 长期沉默销售识别
  - 代表性话术与代表性证据展示

### 6.4 结论中心
- 输出四类结论：
  - 云诊室结论
  - 云管家结论
  - 销售行为结论
  - 产品机会结论
- 每条结论必须配代表证据，不允许只给抽象口号

### 6.5 复核工作台
- 正式查看待复核项
- 查看原文与上下文
- 修改关键字段
- 提交复核结果
- 写回系统

## 7. 最小交付物
本期最小交付物固定为：
- `data/output/insights/v1.5/normalized/` 下的规范化中间层数据
- `data/output/insights/v1.5/reports/` 下的趋势摘要与结论卡产物
- `data/output/insights/v1.5/review/` 下的复核任务与复核结果
- `data/output/insights/v1.5/web/` 下的统一工作台页面
- `docs/releases/v1.5/` 下的完整版本文档
- `data/input/v1.5/` 下的输入基线文档
- 仓库内首批 2 个 skill 的说明文档

## 8. 趋势中心要求
- 默认观察窗口为 `2025-01` 至今
- 固定输出指标：
  - AI 提及量
  - AI 涉及销售人数
  - AI 销售渗透率
  - 主体结构趋势
  - 业务线趋势
  - `confirmed / pending_human_review` 质量趋势
- 趋势图必须能跳到销售或证据，不允许停留在静态图层

## 9. 销售分析中心要求
- 销售必须有稳定主键和归一规则
- 每个销售至少显示：
  - 姓名
  - 区域 / 战区
  - AI 提及次数
  - 覆盖周数 / 月数
  - 主体分布
  - 业务线分布
  - 医生反馈数
  - 潜在机会数
  - 待复核数
  - 代表证据
- 允许区域聚合，但销售个人是最小动作单位

## 10. 结论中心要求
- 结论来自证据簇，不直接来自单条命中
- 每条结论至少包含：
  - 标题
  - 结论说明
  - 对业务的意义
  - 代表证据
  - 涉及销售或区域
  - 可信度
  - 是否需复核
- 必须支持从结论卡回到原始证据

## 11. 复核工作台要求
- `review_queue` 升级为正式任务视图
- 每条任务必须包含：
  - 来源文档
  - 原文片段
  - 进入原因
  - 当前判断
  - 可修改字段
  - 提交记录
- 复核结果必须写回正式结果文件
- 下一轮分析必须消费人工修正结果

## 12. 证据追溯要求
- 所有趋势判断必须回到销售与证据
- 所有结论卡必须回到证据片段
- 所有证据必须回到原文路径
- 页面中不得出现不可追溯的黑盒结论

## 13. 离线产物与 Web 查看关系
本期仍保留离线产物生成机制，但业务查看以 Web 工作台为主。

关系约束如下：
- 离线分析负责生成规范化数据与结论中间产物
- Web 工作台负责展示、下钻和复核
- skill 只辅助趋势和结论生成，不替代工作台和正式分析代码

## 14. 依赖项 / 前置条件
- `v1.2` 下载、归档、审计链路稳定可用
- `v1.4` 试运行产物可作为问题复盘输入
- `v1.3` 冻结样本仍可用于回归
- 销售身份归一规则可由映射表或规则先落地
- 首版复核采用文件回写 MVP，可被业务接受

## 15. 本期明确不做
- 不改 `src/main.py` 的 `v1.2` 主链路职责
- 不做多专题统一平台
- 不做正式数据库方案
- 不做经营结果数据关联
- 不做复杂权限系统
- 不做多人协同工单系统
- 不把 skill 当成正式业务入口

## 16. 验收标准
- 产品负责人能基于工作台回答“现状如何、趋势如何、有哪些机会”
- 销售管理者能基于工作台回答“谁在推动、谁值得复盘、哪里需要赋能”
- 趋势页能稳定回答同比、环比、渗透率和销售活跃度问题
- 销售中心能稳定下钻到销售个人，不以区域汇总代替
- 结论卡必须可追溯到证据和原文
- 复核结果可写回，并在下一轮分析中被消费
- 不影响 `v1.2` 下载、归档、审计和通知主链路
